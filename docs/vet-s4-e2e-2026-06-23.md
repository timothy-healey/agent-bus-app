# DDD Vet — S4 Tauri E2E (WebDriver) harness scaffold

**Target:** `plans/2026-06-23-plan-s4-e2e.md`
**Read alongside:** `DOMAIN.md`, `src-tauri/app/src/lib.rs` (the OHS command surface), `src/wizard/NewProjectWizard.tsx`, `src/wizard/ReviewStep.tsx`, `src/components/Topbar.tsx`, `src/components/ProjectList.tsx`.

## Framing

This is test infrastructure, deliberately light on domain. The council's only legitimate concerns here are: (1) does the harness or its specs **distort a bounded context** (reach past a published surface, place a concept in the wrong context)? (2) do the example specs exercise a **real, OHS-backed flow** rather than a fiction? (3) does the **naming** match the ubiquitous language? (4) is the **scope honesty** (scaffold-only, can't-run-on-macOS) sound and not over-claimed?

The architect's headline read: an E2E harness that drives the app **through its own UI** is the most boundary-respectful kind of test there is — it touches no context's internals, only the published Tauri command surface (the OHS) the way the real user does. The `e2e/` tree imports nothing from `src-tauri/*` or `src/ipc/*`; it talks WebDriver to a running binary. There is no cross-boundary dependency to bake in. That clears the biggest §E risk outright.

What remains are language/honesty findings, not structural ones.

---

### F1 [low] Off-language naming — "smoke"/"e2e" file naming vs the ubiquitous flow it drives — RESOLVED

**What.** The example spec (`create-project.e2e.ts`) drives the wizard's **template-seed** kickoff path, then **create-from-draft**, then **list**. The plan's prose (Task 5) describes the flow well, but the council wants the spec's own language to name the *domain* moments it asserts — "create a project **from a template seed**", "the **Design Session** wizard steps" — using the registered terms (`DOMAIN.md` → *Template (seed)*, *Design Session*, *DraftPipeline*), not generic test-speak. Otherwise the test reads as "click buttons" rather than "exercise the kickoff-via-seed contract", and the next reader can't tell which of the two kickoff paths (generate vs seed) is under test or why.

**Cited plan section.** Task 5 Step 2 (`create-project.e2e.ts`) `describe`/`it` strings; Task 3 selector comments.

**Why it matters.** The language lives in the code — including test code. A spec named in the ubiquitous language documents the contract it pins; one named in generic test-speak documents nothing. (§C / §E off-language.)

**Amendment (apply).** Keep the file names (`*.e2e.ts` is the harness's fencing convention, fine), but ensure the `describe`/`it` titles and a header comment name the registered concepts: **Template (seed)** kickoff (not "a template"), the **Design Session** wizard steps, **create-from-draft**, and state explicitly that the **Generate** (LLM kickoff) path is deliberately *not* under test because it needs a live `claude`. **Status: resolved** — the plan's Task 5 already carries the "template path chosen because Generate needs live claude" rationale; the amendment is to surface that rationale and the registered terms in the spec's own strings. Applied at implementation.

---

### F2 [low] Contradicts `DOMAIN.md`/spec risk — the spec must drive the SEED path, never silently fall back to GENERATE — RESOLVED

**What.** `DOMAIN.md` registers two distinct kickoff paths: the **describe→Generate** one-shot (LLM Chat ACL, needs live `claude`) and the **Template (seed)** path (pure, OHS `seed_template`, no LLM). The whole honesty premise of this item is that E2E runs **without** a live model. If the example spec ever fell back to the Generate path (e.g. because the template picker rendered zero buttons), it would silently require a live `claude` on the CI runner — contradicting the declared scope and turning a "headless-safe" spec into a flaky network-dependent one.

**Cited plan section.** Task 5 Step 2 implementer note ("fall back to the Generate path is NOT acceptable on a headless runner").

**Why it matters.** A test that quietly changes which context it exercises (seed → LLM Chat ACL) under failure conditions is a designed-in boundary lie. (§E contradicts-spec.)

**Amendment (apply).** The plan already states the no-fallback rule and defers a `data-testid` on the template buttons to the live-run `TODO(s4)`. Strengthen it to a hard assertion: the spec must **fail loudly** if no template button is present (`expect(templateButtons.length).toBeGreaterThan(0)`), never proceed via Generate. **Status: resolved** — already present in the plan as `expect(...).toBeGreaterThan(0)`; the amendment is to make the no-silent-fallback contract explicit in the spec comment. Applied at implementation.

### F3 [info] Unowned-shared-type check — `e2e/helpers/selectors.ts` is harness-local, not a kernel — RESOLVED (no action)

**What.** The plan adds a shared `selectors.ts` consumed by both specs. The council checks: is this an accidental shared kernel that needs an owner? **No** — it is a within-harness DRY helper (one test tree, one consumer set), not a type crossing a context line. It holds UI selector strings, no domain types. It mirrors the UI's aria-labels/text; the source-of-truth comments point back at the real components so a UI rename is a one-file fix.

**Cited plan section.** Task 3.

**Why it matters.** Worth stating explicitly so a future reader doesn't mistake it for a published contract. (§E unowned-shared-type — checked, cleared.)

**Amendment.** None. **Status: resolved** (no action). Noted for the record.

---

### F4 [low] Scope-honesty — the macOS-can't-run claim must be carried in the README, backlog, AND the runner's own behaviour — RESOLVED

**What.** The honesty premise (`tauri-driver` has no macOS backend; WKWebView exposes no WebDriver) is correct and matches `DOMAIN.md`'s stack note ("native webview (WebKit/WebView2/WebKitGTK)"). The risk is honesty that lives only in prose: a doc says "macOS unsupported" but the harness would still *attempt* to run and produce a confusing failure, or someone marks the backlog "done" reading the green root suite. The claim must be **load-bearing in three places**: the README (prose), the backlog (status wording), and the **runner + config refusing to run on Darwin with a clear message** (behaviour, not just docs).

**Cited plan section.** Honesty section; Task 4 `onPrepare` Darwin guard; Task 6 `run-e2e.sh` Darwin guard; Task 7 README; Task 10 backlog.

**Why it matters.** Scope honesty is a first-class deliverable for this item. A claim only in prose drifts; a claim enforced in code can't be accidentally violated. (§E contradicts-spec — guarding against an over-claim.)

**Amendment (apply).** The plan already enforces the Darwin guard in **both** `wdio.conf.ts:onPrepare` and `run-e2e.sh`, and marks the backlog scaffold-only. Confirm all three carriers ship and the backlog wording never reads a clean "done". **Status: resolved** — present in the plan; the amendment is to verify all three at merge. Applied.

---

## Verdict

**SOUND WITH FIXES.** No structural DDD problems: the harness drives the app through its published OHS via the real UI, importing no context internals and introducing no shared kernel — the most boundary-respectful test shape available. The example flow (Template-seed kickoff → create-from-draft → list) exercises a real, headless-safe contract across Pipeline Authoring + Workspace, and is correctly chosen over the live-`claude` Generate path. All four findings are low/info language-and-honesty fixes, all already substantially present in the plan; the resolutions are to surface the registered ubiquitous-language terms in the spec strings (F1), make the no-silent-fallback-to-Generate contract explicit (F2), note the selectors helper is harness-local not a kernel (F3, no action), and verify the macOS-can't-run claim is load-bearing in README + backlog + runner behaviour (F4). Proceed to implementation.

**No finding requires refactoring existing code first.** No finding bounces to redesign.
