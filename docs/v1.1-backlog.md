- [ ] **T-ToolArgs · Validate terminal agentic tool-call args against real per-tool `input_schema`s** — `backlog` — the god terminal's within-turn agentic loop (C1) validates a model-emitted `{tool, args}` block **only by tool name** against the `ToolCatalog`; the published `input_schema`s are empty `{"type":"object"}` placeholders, so malformed/missing `args` reach the supplier's `RootDispatcher` unchecked and fail late (or silently mis-dispatch). Harden the terminal the same way DS-Schema hardened the Design Session: give each supplier OHS tool a **real `input_schema`** (derive it from the dispatch arg types — `schemars` on the per-tool arg structs, mirroring the slice-schema work) so the catalog publishes the true shape; **validate `args` against that schema before dispatch**; on a miss, do a **bounded repair turn** (re-prompt the model on the same `dialogue_id` naming the specific arg error, ≤2 retries) instead of a late/silent failure. This is the CLI-path twin of DS-Schema for Conversational Control — same constraint applies (`claude --print` can't force tool-use, so it's schema-in-the-loop + validate + repair, not native tool-use). Touches `conversational_control` (the `ToolCatalog`/agentic-loop kernel) + each supplier's OHS arg types; keep the suppliers' boundaries intact (each owns its own tool arg schema). Pairs with **N-NativeToolUse** below (the API-path version). Source: DS-Schema follow-up; C1 composite-engine loop only checks the tool name today.
- [ ] **N-NativeToolUse · Native tool-use / structured output via the anthropic-api runner (R1)** — `backlog` — the **strongest** version of both DS-Schema and T-ToolArgs, available **only on the API path** (the R1 `anthropic-api` runner — design doc §v1 boundary 4 / R1 backlog), NOT the claude-cli path. Pairs with DS-Schema (CLI-path prompt+repair) and T-ToolArgs (CLI-path terminal validation): those two are the universal fallback; this is the forced-correctness upgrade where the API runner is in play. ## Parallel flow (fork/join)

- [x] **P1 · Nested groups / non-linear lanes** — `done` (tag `plan-p1-nested-groups`) — lifts the flat-linear-lane restriction: a fork lane may now contain a **gate** and/or a **nested fork** (a child `FanOutGroup`). `FanOutGroup` is **recursive** via an optional parent link — `parent_group_id` + `parent_lane` (migration `008_nested_groups.sql`, two nullable columns on `fanout_groups`; append-only, 001–007 untouched; registered in BOTH `app/src/lib.rs` migration lists + the `user_version` test bumped 7→8). A nested fork inside a lane expands (the same `expand_fork` path as a top-level fork) into a **child group** carrying the enclosing group id + lane; when the child group's barrier completes, its continuation is mapped to a **parent-lane verdict** (`FanOutGroup::parent_lane_verdict`: downstream ⇒ approve, needs-human ⇒ reject) and recorded at the **parent group's barrier** via the SAME `record_and_try_complete`/quorum/early-cancel methods — the SAME `UPDATE fanout_groups SET completed=1 WHERE id=? AND completed=0` single-writer guard, one level up. **Exactly-once-completion is preserved per group row, independently at every level**: child-complete and parent-settle are deliberately SEPARATE single-row-guarded writes (reference by id, no cross-root transaction); a concurrent-straggler test proves exactly-once at the nested level. The lane-walk is hierarchical in BOTH the runtime (`lane_reaches`: team→on_approve, gate→downstream, fork→nested join's downstream) and validation (`check_lane_reachable` replaces `check_lane_linear`), bounded at **max nesting depth 3** (`NestingTooDeep`); best-effort validation drops the old no-gate-in-a-lane rule. Flat lanes + P2 early-cancel + P3 quorum paths unchanged (root groups carry `parent=None` and spawn the continuation as before). **Backend-heavy — no frontend surface** (nested lanes do not yet render distinctly in PipelineView; a hierarchical viewer is deferred to the impeccable pass alongside the deferred P2/P3 authoring controls).
